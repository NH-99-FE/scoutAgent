# Scout Agent 是怎样记录文件 Diff 的

这篇文档只回答一件事：**AI 改完文件后，Scout 怎样知道改了什么，并把结果展示给用户。**

---

## 先说结论

当 AI 用 `edit` 或 `write` 修改文件时，Scout 会：

1. 在修改前记住文件原来的内容。
2. 修改成功后记住文件现在的内容。
3. 比较这两份内容，得到 Diff。
4. 把 Diff 的关键信息保存到会话里。
5. 用户点开“查看变更”时，再把 Diff 发给界面显示。

这样做的好处是：用户看到的是 **AI 这一次真正写进去的内容**，而不是后来文件又被改过之后的内容。

---

## 用一个例子理解

假设原文件是：

```ts
function greet(name: string) {
  return `Hello, ${name}`;
}
```

AI 把它改成：

```ts
function greet(name: string) {
  return `Hi, ${name}!`;
}
```

Scout 记录的不是“这个文件现在长什么样”，而是：

```diff
 function greet(name: string) {
-  return `Hello, ${name}`;
+  return `Hi, ${name}!`;
 }
```

如果之后 AI 又把文件改成别的样子，第一轮的 Review 仍然保留上面这次修改的 Diff。

---

## 整个流程

```text
AI 调用 edit / write
        ↓
Scout 在写入前保存“修改前”
        ↓
文件真正写入成功
        ↓
Scout 保存“修改后”
        ↓
计算 Diff
        ↓
保存到当前会话
        ↓
用户展开时才显示到界面
```

这里最重要的是：**只有文件真的写成功后，Scout 才把它记为一次修改。**

这样可以避免模型说“我修改了”，但实际上文件写失败时，界面却错误显示变更。

---

## 为什么不能在用户点开 Diff 时再比较当前文件

因为“当前文件”可能已经不是当时 AI 写完后的版本了。

例如：

```text
10:00  AI 第一次改了 a.ts
10:01  用户手动继续改了 a.ts
10:02  用户点开 10:00 的 Diff
```

如果 10:02 才读取文件并计算 Diff，看到的会混入用户 10:01 的修改，不再是 AI 第一次改动的真实结果。

所以 Scout 要在 **写入当时** 就计算并保存 Diff。

---

## 一次回答里改同一个文件很多次怎么办

AI 一次回复可能连续改同一个文件：

```text
第一次修改：A0 → A1
第二次修改：A1 → A2
第三次修改：A2 → A3
```

用户通常更关心这一轮最后造成的效果，因此 Scout 最终保存：

```text
本轮开始时：A0
本轮结束时：A3
最终 Diff：A0 → A3
```

它不会把三份完整文件都长期保存，否则同一个大文件连续修改几次，内存和会话文件都会快速变大。

但 Scout 仍会记住“这一轮一共调用过哪几次 edit/write”，用于关联工具调用和展示历史。

---

## `MutationJournal` 是什么

可以把它理解成“本轮文件修改的账本”。

它负责记录：

- 哪个文件被改了；
- 这一轮里改了几次；
- 最初版本是什么；
- 最终版本是什么；
- Diff 是否已经计算完成；
- 哪次工具调用导致了修改。

它的作用是避免不同模块各自保存一份状态。

```text
错误做法：
工具层记一份、Host 记一份、UI 再记一份

Scout 的做法：
MutationJournal 统一记事实，其他模块按需读取
```

---

## `DiffDocument` 是什么

`DiffDocument` 就是 Scout 保存的标准 Diff 格式。

它包含：

- 增加了多少行；
- 删除了多少行；
- 第一个变化发生在哪一行；
- 哪些行被删除；
- 哪些行被增加；
- 变化附近的少量上下文；
- 修改前后内容的指纹。

内容指纹类似文件内容的身份证：

```ts
{
  size: 1234,
  sha256: "..."
}
```

它用于判断“现在的文件是否仍然等于当时修改完成后的文件”。

### 为什么叫 canonical

意思是“唯一标准版本”。

聊天里的小 Diff、完整 Changes Review 页面、增删行统计，全部从同一份 `DiffDocument` 生成。

不会出现：

```text
聊天显示 +10 -2
完整页面显示 +9 -3
```

因为它们都不自己重新计算，而是读取同一个结果。

---

## 为什么要用 Worker 计算 Diff

比较大文件可能比较耗 CPU。

如果在 Extension 主线程里计算，用户可能会感觉：

- VS Code 扩展卡顿；
- 工具状态更新变慢；
- 界面消息延迟。

所以 Scout 把 Diff 计算交给单独 Worker。主线程继续负责工具生命周期、会话和 UI 通信。

---

## 如果 AI 连续很快地改同一个文件呢

可能出现这种情况：

```text
第一次修改已经开始算 Diff，但还没算完
第二次修改已经发生
```

Scout 会给每次文件变更一个递增编号，叫 `revision`。

```text
revision 1：旧结果，正在计算
revision 2：新结果，已经发生
```

如果 revision 1 最后才返回，Scout 会丢掉它，只接受 revision 2。

这样用户不会看到旧 Diff 覆盖新 Diff。

---

## 什么时候保存到会话里

AI 一次回答结束时，Scout 会做三件事：

1. 确认这一轮不会再继续写文件。
2. 等待正在计算的 Diff 完成。
3. 把最终 Diff 写进 session。

这个保存结果叫作 artifact，可以理解为“这轮文件变更的存档”。

它是隐藏数据，不会作为聊天树里的普通消息显示，但可以在恢复会话时重新用于展示 Review。

---

## 保存了什么，没有保存什么

### 保存

- 哪个 turn 产生的修改；
- 哪个文件被改；
- 哪些工具调用参与了修改；
- 增加、删除的行；
- 关键 Diff hunk；
- 修改前后内容的 fingerprint；
- Diff 是否完整或已降级。

### 不保存

- 完整修改前文件；
- 完整修改后文件；
- UI 的滚动位置和展开状态；
- syntax highlight 的 token；
- 被省略的整段中间代码。

不保存完整文件的原因很简单：会话文件不能因为修改几个字就额外复制几 MB 文件内容。

---

## 为什么界面不是一开始就加载全部 Diff

用户不一定会点开每个文件。

因此 Scout 初始只发送摘要：

```text
src/a.ts  +12 -4
src/b.ts  +3 -0
```

用户点击某个文件后，界面才请求该文件的详细 Diff。

这能减少：

- 初始消息大小；
- Webview 渲染量；
- 语法高亮开销；
- 大会话恢复时间。

聊天里的 Diff 也有更小的上限；完整 Changes Review Panel 则允许加载更多 hunk，但仍然分批加载。

---

## 大文件、二进制文件怎么办

不是所有文件都适合生成文本 Diff。

以下情况，Scout 会明确标记为“无法完整审查”，但不会影响写文件：

- 二进制文件；
- 非 UTF-8 文本；
- 文件太大；
- Diff 行数太多；
- Diff Worker 超时；
- 修改前或修改后内容不可用。

这样做的原则是：

> 文件是否写成功，和是否能生成漂亮的 Review，是两件事。

不能因为 Review 太大，就把已经正确完成的写操作说成失败。

---

## 当前限制：为什么中间省略的代码不能展开

为了控制会话大小，当前 `DiffDocument` 只保存变更附近的少量上下文，默认是 3 行。

例如：

```diff
  上下文第 1 行
  上下文第 2 行
  上下文第 3 行
  ... 省略 200 行 ...
  上下文第 4 行
  上下文第 5 行
  上下文第 6 行
```

那 200 行文本当前没有保存在 artifact 中，因此页面只能显示“省略 200 行”，不能真正展开。

这是一个有意识的取舍：

| 选择 | 好处 | 代价 |
|---|---|---|
| 保存全部中间代码 | 历史 Diff 可完整展开 | JSONL 会明显变大 |
| 只保存少量上下文（当前） | 会话小、恢复快 | 中间代码不能展开 |

---

## 后续可以怎样低成本支持展开

一种成本较低的方案是：

1. 用户点击“省略 N 行”。
2. Scout 读取当前文件。
3. 比较当前文件 fingerprint 是否等于当时 artifact 的 `afterFingerprint`。
4. 如果完全一致，说明文件没变过，可以安全展示中间代码。
5. 如果不一致，显示“文件已继续修改，无法展开历史上下文”。

优点：JSONL 基本不会变大。

限制：文件后来被用户或 AI 改过、删除过、切换分支后，就无法展开历史内容。

---

## 能不能支持撤销

可以支持“安全撤销这一轮修改”，但需要做检查。

过程是：

1. 读取当前文件。
2. 确认它的 fingerprint 仍等于当时 AI 修改后的 fingerprint。
3. 将 Diff 反过来应用。
4. 再确认结果等于修改前 fingerprint。

这能避免覆盖用户后续修改。

但当前更适合撤销整个 turn，而不是撤销这个 turn 里面某一次单独的工具调用。

---

## 面试时怎么回答

可以这样说：

> 我们不在用户点开页面时才比较当前文件，因为当前文件可能已经被后续修改，历史结果会漂移。我们在 edit/write 真正写入成功后捕获 before/after，并按 turn 和文件聚合。Diff 由 Worker 计算成唯一的 DiffDocument，聊天摘要和完整 Review 都从这个 document 投影。完成一个 turn 后再把结果以有界 artifact 写进 session。工具结果只带轻量引用，完整 Diff 和 tokens 都按需加载。这样既保证了历史准确，也避免了模型上下文、JSONL 和 UI 渲染被大文件拖垮。

## 术语速查

| 术语 | 人话解释 |
|---|---|
| turn | AI 处理一次用户消息到结束的一整轮工作 |
| mutation | 一次真实写入文件的事实 |
| MutationJournal | 本轮文件修改的账本 |
| baseline | 本轮开始前的文件版本 |
| after | 本轮结束后的文件版本 |
| revision | 同一文件第几次更新，用来防止旧结果覆盖新结果 |
| DiffDocument | Scout 唯一标准的 Diff 数据 |
| artifact | 写入 session 的历史变更存档 |
| fingerprint | 文件内容的身份证，用于判断内容是否一致 |
| lazy load | 用户真正点开时才加载详细数据 |
